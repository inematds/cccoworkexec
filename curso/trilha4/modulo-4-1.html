📁 Projetos e raio de impacto

Um Project no Claude.ai não é uma pasta de chats — é um sandbox com 200K tokens, custom instructions e knowledge files compartilhados. Aprender a desenhar o "raio de impacto" mata 80% dos erros mais comuns de "Claude esqueceu" ou "está alucinando".

📁 O que é um Projeto

Project (claude.ai) agrupa chats com contexto persistente: 200K tokens (~500 páginas), custom instructions e knowledge files. Disponível em Pro, Max, Team e Enterprise. Cada chat dentro do projeto herda automaticamente esses três elementos.

🧱 Os 3 pilares de um Project

  • •Janela de 200K tokens: ~500 páginas de contexto disponível em cada chat. Não é compartilhado entre chats — é por chat, mas o que está abaixo (instructions + files) é injetado em todos.
  • •Custom Instructions: system prompt do projeto, definido na UI. Persona, tom, restrições, domínio.
  • •Knowledge files: PDFs, docs, imagens, planilhas que ficam disponíveis em cada conversa do projeto.

✓ Quando faz sentido criar Project

  • ✓Cliente recorrente com material próprio
  • ✓Persona específica (revisor jurídico, copywriter)
  • ✓Domínio com vocabulário próprio (medicina, fintech)
  • ✓Workflow repetido 3+ vezes por semana

✗ Quando NÃO criar Project

  • ✗Pergunta one-off ("traduz isso")
  • ✗Experimento sem reuso planejado
  • ✗Misturar 3 clientes "pra economizar"
  • ✗"Project geral" que vira lixo de contexto

💡 Dica prática

Pense em Project como uma "máquina" preparada pra uma classe de tarefa. Você não cria projeto pra uma conversa — cria pra todas as conversas daquela classe.

2

💥 Raio de impacto — escopo isolado

"Raio de impacto" = tudo que aquele projeto enxerga e influencia. Chats fora do projeto não veem suas instructions nem files. Dois projetos nunca trocam contexto entre si.

🔬 Por que o conceito importa

A maior causa de "Claude começou a inventar coisas" é mistura de escopos: você cola material do cliente A num projeto que já tinha material do cliente B. Claude vê os dois e cruza informações que não deveriam se cruzar.

Mantendo raios disjuntos, a memória do projeto fica limpa, previsível e auditável.

1

Antes — tudo num só

Project "Trabalho"

Contém docs do cliente A, contratos do cliente B, copy da campanha C. Claude começa a misturar: cita o cliente A num e-mail pro cliente B. Raio de impacto = caos.

2

Depois — um por escopo

3 projects independentes

"Cliente A — Vendas", "Cliente B — Contratos", "Campanha C — Copy". Cada um vê só o que importa. Cross-talk zero.

3

Manutenção — arquivar

Quando o cliente vai embora

Project encerrado fica arquivado. Não polui a lista de projetos ativos, mas a memória continua acessível se precisar.

3

🆕 Quando criar projeto novo vs continuar

Critério prático: mudou o "personagem" (cliente, domínio, tom) — novo project. Mesma classe de tarefa em série — mesmo project. Não fragmente por capricho, não acumule por preguiça.

✓ Triggers para criar NOVO

  • ✓Cliente novo entra na lista
  • ✓Tom muda (formal corporativo → casual marketing)
  • ✓Domínio muda (jurídico → médico)
  • ✓Conjunto de knowledge files diferente

✗ Triggers FALSOS

  • ✗"Tarefa diferente" do mesmo cliente
  • ✗Mês diferente do mesmo workflow
  • ✗Conversa antiga "muito longa"
  • ✗"Vou criar pra testar e apagar"

💡 Dica prática

Regra de bolso: se você fosse trocar de persona/tom/restrição no system prompt, é novo project. Se fosse só trocar a tarefa específica, é só novo chat no projeto existente.

4

📚 Knowledge files — 30 MB por arquivo

Arquivos colados num project ficam disponíveis em toda conversa daquele project. Limite por arquivo: 30 MB. Número de arquivos: ilimitado, desde que o total caiba na janela de contexto.

📑 Tipos suportados

  • PDFs < 100 páginas: análise visual + texto (Claude vê layout e imagens)
  • PDFs > 1000 páginas: extração apenas de texto
  • Documentos não-PDF: extração de texto somente
  • Imagens: PNG, JPG, GIF, WebP — visão multimodal

📋 Estrutura típica de knowledge num project corporativo

knowledge/
├── 01-empresa-overview.md        (3 KB — quem somos)
├── 02-tom-de-voz.md              (5 KB — style guide)
├── 03-produtos-catalogo.pdf      (1.2 MB — 60 pgs, visual+texto)
├── 04-faqs-clientes.md           (45 KB — perguntas reais)
├── 05-base-juridica.pdf          (8 MB — contratos modelos)
└── 06-glossario-termos.md        (12 KB — vocab interno)

Total: ~9 MB. Cabe folgado. Cada chat herda automaticamente.

📜 Instruções persistentes (Custom Instructions)

Custom Instructions é o system prompt do projeto. Injetado em toda conversa do project, sem limite documentado de caracteres além do que cabe no contexto. É onde você define persona, tom, restrições — não tarefas específicas.

📋 Estrutura recomendada (3 blocos)

# ROLE
Você é um revisor de contratos do escritório XYZ.
Tem 15 anos de experiência em direito societário.
Foco: contratos M&A e SPA.

# STYLE
- Português formal, jurídico, mas claro
- Sempre cite a cláusula específica
- Marque riscos como [ALTO] [MÉDIO] [BAIXO]

# CONSTRAINTS
- Nunca aconselhe ação que requeira OAB sem ressalva
- Se ambíguo, peça contexto extra
- Não invente jurisprudência

💡 Dica prática

Mantenha uma cópia das instructions em um arquivo instructions.md no knowledge do projeto. A UI da Anthropic não tem histórico de versões — sem cópia, você perde a versão anterior pra sempre.

6

🗂️ Estrutura de pastas mentais

Sua lista de projects é uma biblioteca navegável, não um histórico de experimentos. Adote nomenclatura clara, mantenha 5-10 ativos, arquive o resto.

🏷️ Padrão de nome

Use o formato "Contexto — Tema". Cliente, projeto interno, pessoal.

  • ✓ Acme Corp — Propostas
  • ✓ Pessoal — Estudo IA
  • ✓ Interno — Code Review
  • ✗ teste1, geral, misc

✓ Higiene de projetos

  • ✓5-10 projects ativos
  • ✓Revisão mensal — arquivar inativos
  • ✓Nome descritivo, não sigla
  • ✓1 escopo por project

✗ Anti-padrões

  • ✗30+ projects ativos
  • ✗Nomes tipo "teste", "novo", "ok"
  • ✗"Project geral" pegando tudo
  • ✗Nunca arquivar — lista enorme
